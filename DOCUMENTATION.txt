================================================================================
  1. RAPPEL DU CONTEXTE ET DES TÂCHES
================================================================================

  Le cours introduit les Pattern Functional Dependencies (PFDs) comme une
  extension des Functional Dependencies (FDs) classiques adaptée aux données
  réelles, bruitées et semi-structurées.

  UNE PFD est une règle de la forme :
      "si col_X correspond au pattern P1, alors col_Y correspond au pattern P2"
  Notation formelle : R(X -> Y, Tp)  où Tp est un tableau de patterns.

  UNE PFD APPROXIMATIVE tolère un taux d'exception epsilon :
      confiance = |{ t : t |= P1 ET t |= P2 }| / |{ t : t |= P1 }|
      La PFD est valide si confiance >= (1 - epsilon)

  TÂCHES DEMANDÉES (extrait du sujet) :

================================================================================
  4. MODULE DE VALIDATION — pfd_verifier.py
================================================================================

  RÔLE DANS LE PROJET
  -------------------
  Première brique implémentée. C'est le module le plus fondamental :
  il calcule si une PFD candidate est valide étant donné un epsilon.
  Il est utilisé par tous les autres modules (le pipeline l'appelle à l'étape 3,
  le généraliseur l'appelle pour revalider les règles fusionnées).

  LIEN AVEC LE COURS
  ------------------
  Implémente directement les formules des slides 7-8 :
    - support(X) = |{ t ∈ R | t |= P1 }|               → n_matching_X
    - conf(X->Y) = |{ t : t |= P1 ET t |= P2 }|        → confidence
                   ────────────────────────────
                        support(X)
    - noise = 1 - conf(X->Y)                            → n_violations / n_matching_X
  Correspond à l'étape 4 du pipeline de découverte classique (slide 14) :
  "Validate candidate dependencies — compute support and confidence".

  FONCTIONS EXPOSÉES
  ------------------
  _match_pattern(series, pattern, match_type)
      Fonction interne. Applique le matching sur une colonne pandas.
      Supporte 4 types :
        "exact"      : égalité stricte (series == pattern)
        "startswith" : la valeur commence par le pattern (après cast str)
        "contains"   : la valeur contient le pattern
        "regex"      : expression régulière Python (re.compile)
      Les valeurs NaN ne matchent jamais.
      Lien cours : "Patterns can be prefixes, substrings, regular expressions"
                   (slide 4).

  verifier_pfd(df, col_X, pattern_X, col_Y, pattern_Y, epsilon, ...)
      Fonction principale. Applique les masques X et Y et calcule les métriques.
      Paramètres étendus : match_type_X et match_type_Y permettent des types
      différents pour les deux côtés de la règle (ex. startswith pour X,
      exact pour Y) — cas fréquent dans les données réelles.
      Retourne un dict : confidence, is_valid, n_matching_X, n_valid,
                         n_violations, epsilon, examples_violations.

  rapport_pfd(...)
      Wrapper d'affichage. Appelle verifier_pfd et formate le résultat.
      Utile pour la démonstration (Tâche 3, démo 15 min).

  BLOC DE DÉMONSTRATION (__main__)
  ---------------------------------
  6 tests sur les 4 datasets réels, couvrant les cas mentionnés dans
  l'énoncé du projet :
    Test 1 : FD exacte Department -> Department Name (t1, epsilon=0.0)
             → Vérifie la notion de FD exacte (confidence=100%, 0 violation)
    Test 2 : Gender='F' -> Fulltime-Regular (t1, epsilon=0.1)
             → PFD approx. invalide (conf=81%, violée par les femmes à temps partiel)
    Test 3 : Zip=20852.0 -> 'ROCKVILLE' (t3, epsilon=0.05)
             → Cas de violations réelles (NORTH BETHESDA dans le même ZIP)
    Test 4 : Licensee Number sw 'BBW' -> 'On Premise' (t3, epsilon=0.1)
             → PFD par préfixe valide (conf=95.1%)
    Test 5 : ZIP sw '606' -> 'Chicago' (t2, epsilon=0.1)
             → Préfixe ZIP classique (conf=98.3%, 37 violations de casse)
    Test 6 : ref_type='PubMed' -> ref_url sw europepmc (CHE, epsilon=0.05)
             → PFD avec matching asymétrique (exact côté X, startswith côté Y)


================================================================================
  5. MODULE D'EXTRACTION DE PATTERNS — src/pattern_extractor.py
================================================================================

  RÔLE DANS LE PROJET
  -------------------
  Étape 1 du pipeline de découverte classique.
  Transforme les valeurs brutes d'une colonne en patterns candidats,
  regroupés par les lignes qui les "matchent".

  LIEN AVEC LE COURS
  ------------------
  Implémente directement les slides 9-10 ("1. Pattern Extraction") :
    "Extract candidate patterns from attribute values"
    "Tokens, substrings, prefixes, n-grams"
    "Use frequency thresholds — Index patterns efficiently"
  Et les slides 16-17 (Running Example, étape 1) :
    "name='John Smith' → first_token(name)='John'"
    "zip=90012 → prefix(zip,3)='900'"

  FONCTIONS SUR UNE VALEUR UNIQUE
  --------------------------------
  extract_prefixes(value, k_max=5)
      "ABCDE" → ["A", "AB", "ABC", "ABCD", "ABCDE"]
      Implémente prefix(zip, k) du cours.
      Gère les non-string (retourne []).

  extract_tokens(value)
      "John Smith" → ["John", "Smith"]
      Implémente first_token(name) du cours.
      Séparateurs : espaces, tirets, underscores, /, virgule, point-virgule.

  extract_ngrams(value, n=3)
      "90012" → ["900", "001", "012"]
      Complémentaire aux préfixes pour capturer des patterns internes.

  FONCTIONS SUR UNE COLONNE ENTIÈRE
  -----------------------------------
  prefix_patterns(series, k_max, min_support)
      Retourne {pattern: [row_indices]} pour tous les préfixes ayant
      au moins min_support occurrences.
      Les colonnes numériques (float, int) sont converties en str.
      C'est la principale source de patterns pour le pipeline.

  token_patterns(series, min_support)
      Retourne {premier_token: [row_indices]}.
      Utile pour les colonnes de noms ("Full Name", "Position Title").

  exact_patterns(series, min_support)
      Retourne {valeur_exacte: [row_indices]}.
      Utilisé comme point de départ pour la généralisation.

  extract_all_patterns(series, k_max, min_support)
      Point d'entrée unifié. Retourne un dict structuré :
      { "startswith": {...}, "first_token": {...} }
      Appelé par pfd_discovery.py pour chaque colonne.

  NOTE ARCHITECTURALE
  -------------------
  Ce module ne dépend que de pandas et re. Il peut être réutilisé
  indépendamment pour la Tâche 2 (le workflow agentique peut aussi
  appeler extract_all_patterns pour préparer les features à soumettre
  au LLM).


================================================================================
  6. MODULE DE GÉNÉRATION DE CANDIDATS — src/candidate_generator.py
================================================================================

  RÔLE DANS LE PROJET
  -------------------
  Étape 2 du pipeline. À partir des patterns extraits, génère toutes
  les paires (col_X, pattern_X, col_Y, valeur_Y) candidates à tester.

  LIEN AVEC LE COURS
  ------------------
  Implémente les slides 12-13 ("3. Candidate Generation") :
    "Generate candidate dependencies of the form X -> Y"
    "Each attribute may have multiple pattern representations"
    "first_token(name), prefix(zip,3), domain(email)..."
  La stratégie "valeur la plus fréquente de Y dans le groupe X" est
  une heuristique standard de découverte de FDs (slide 18 : "check
  whether Y is consistent within each group").

  FONCTIONS
  ---------
  _most_common_value(series)
      Pour un sous-ensemble de lignes, retourne la valeur de Y la plus
      fréquente ainsi que son décompte et le total non-null.
      C'est l'heuristique qui détermine le "pattern_Y" candidat.

  generate_candidates(df, col_X, pattern_map, match_type, target_cols, ...)
      Pour chaque (pattern_X, col_Y) :
        1. Isole les lignes via les indices de pattern_map
        2. Calcule la valeur modale de col_Y
        3. Crée un candidat structuré
      match_type "first_token" est converti en "startswith" pour
      compatibilité avec pfd_verifier.

  generate_all_candidates(df, pattern_maps, target_cols, ...)
      Itère sur toutes les colonnes sources et tous les types de patterns.
      Dédoublonne les candidats identiques (clé = 5-uplet).
      Retourne la liste complète des candidats à valider.

  NOTE SUR LES PERFORMANCES
  --------------------------
  Pour t2.csv (3 502 lignes × 13 colonnes), le module génère ~5 000
  candidats en < 1 seconde. Le goulot d'étranglement est la validation
  (étape 3), pas la génération.


================================================================================
  7. MODULE DE GÉNÉRALISATION — src/rule_generalizer.py
================================================================================

  RÔLE DANS LE PROJET
  -------------------
  Étape 4 (dernière) du pipeline. Réduit le nombre de règles en fusionnant
  les règles spécifiques en règles plus générales et en éliminant les
  redondances.

  LIEN AVEC LE COURS
  ------------------
  Implémente directement les slides 14-15 ("5. Generalization of Patterns") :
    "Merge specific patterns into more general and meaningful rules"
    Exemple du cours :
      "John*" → M  +  "James*" → M  →  first_token(name) → M
    "Why generalize? Reduce redundancy, improve interpretability"
    "Trade-off: more general rules may have lower confidence"
  Et le slide 15 : "Generalized rule must maintain confidence >= theta"

  FONCTIONS
  ---------
  _longest_common_prefix(strings)
      Calcule le PGCP (plus grand préfixe commun) de plusieurs chaînes.
      Ex. : ["606", "6066", "60601"] → "606"
      Utilisé pour trouver le pattern généralisé d'un groupe de règles.

  fuse_rules(valid_pfds, df, epsilon)
      Algorithme principal de fusion :
      1. Groupe les règles ayant même (col_X, col_Y, pattern_Y)
      2. Pour chaque groupe à ≥ 2 règles, calcule le PGCP des pattern_X
      3. Revalide la règle généralisée via verifier_pfd
      4. Si valide : remplace le groupe par une seule règle générale
         Si invalide : conserve les règles spécifiques
      Exemple observé sur t3.csv :
        "BBW1*" → On Premise + "BBW2*" → On Premise + ... → "B*" → On Premise
        (la lettre initiale 'B' suffit à prédire le Channel Type)

  prune_dominated(rules)
      Élagage des règles dominées :
      Une règle A (pattern PA, startswith) domine B (pattern PB, startswith)
      si PA est un préfixe strict de PB et les deux ont même (col_X, col_Y, Y).
      Dans ce cas B est inutile (A couvre tous les cas de B et plus).
      Ex. : si "6" → Chicago ET "606" → Chicago, "606" est élagué.

  generalize_rules(valid_pfds, df, epsilon)
      Point d'entrée : applique fuse_rules puis prune_dominated.
      Appelé en fin de pipeline par pfd_discovery.discover().

  RÉSULTAT SUR LES DONNÉES RÉELLES
  ----------------------------------
  t2.csv : 1087 règles valides → 324 après généralisation/élagage (-70%)
  t3.csv : 30 règles valides → 6 après généralisation/élagage (-80%)
  t1.csv : résultats similaires — forte réduction des règles redondantes

  Ce taux de réduction illustre le problème de la prolifération de patterns
  évoqué au slide 9 ("Very large number of patterns, many are irrelevant").


================================================================================
  8. PIPELINE PRINCIPAL — pfd_discovery.py
================================================================================

  RÔLE DANS LE PROJET
  -------------------
  Orchestre les 4 étapes de la Tâche 1 en un pipeline utilisable en ligne
  de commande. C'est le point d'entrée principal du projet.

  LIEN AVEC LE COURS
  ------------------
  Implémente la Pipeline complète des slides 8-9 :
    Étape 1 : Pattern Extraction   → src/pattern_extractor.py
    Étape 2 : Pattern Grouping     → src/candidate_generator.py (indices par pattern)
    Étape 3 : Validation           → pfd_verifier.verifier_pfd
    Étape 4 : Generalization       → src/rule_generalizer.generalize_rules
  (Note : l'étape "Candidate Generation" du cours correspond à la
   combinaison de nos étapes 1+2 : extraction + appariement avec col_Y)

  FONCTION PRINCIPALE
  -------------------
  discover(df, epsilon, min_support, k_max, verbose)
      Enchaîne les 4 étapes.
      Paramètres clés :
        epsilon      : tolérance aux violations (cours : "noise threshold")
        min_support  : filtre les patterns trop rares (cours : "support >= K")
        k_max        : longueur maximale des préfixes (cours : "prefix(zip, k)")
      Retourne les règles triées par confiance décroissante.
      Affiche un résumé à chaque étape si verbose=True.

  INTERFACE CLI
  -------------
  python pfd_discovery.py --dataset <fichier.csv> [options]

  Options :
    --epsilon      Tolérance (défaut 0.05)
    --min-support  Support minimum (défaut 10)
    --k-max        Longueur max des préfixes (défaut 5)
    --top N        Afficher les N meilleures règles
    --cols A B ... Restreindre l'analyse à certaines colonnes
    --output       Fichier CSV de sortie personnalisé
    --quiet        Pas de messages de progression

  Exemples :
    # Découverte large sur t2
    python pfd_discovery.py --dataset data/pfd_validation/t2.csv --epsilon 0.1

    # FD exactes sur t1 (colonnes Department/Department Name uniquement)
    python pfd_discovery.py --dataset data/pfd_validation/t1.csv \
        --epsilon 0.0 --cols Department "Department Name"

    # Découverte rapide sur t3
    python pfd_discovery.py --dataset data/pfd_validation/t3.csv \
        --min-support 20 --epsilon 0.1 --top 10

  FONCTIONS D'AFFICHAGE ET D'EXPORT
  -----------------------------------
  print_results(pfds, top_n)
      Tableau formaté : numéro, règle, confiance, support, violations.
      Les règles généralisées sont marquées d'un astérisque (*).

  export_csv(pfds, path)
      Exporte dans results/discovered_pfds_<dataset>.csv.
      Colonnes : col_X, pattern_X, match_type_X, col_Y, pattern_Y,
                 match_type_Y, confidence, n_matching_X, n_valid,
                 n_violations, epsilon, generalized_from.

  ── data/pfd_validation/t1.csv ─────────────────────────────────────────────

  Source    : Comté de Montgomery (Maryland, USA), registre des employés.
  Lignes    : 9 101
  Colonnes  : Full Name, Gender, Department, Department Name, Division,

    - Department sw 'F'  → Assignment Category = 'Fulltime-Regular' (100%)

  ── data/pfd_validation/t2.csv ─────────────────────────────────────────────

  Source    : Ville de Chicago, registre des employeurs.
  Lignes    : 3 502
  Colonnes  : Year, EMPLOYER_ID, NAME, ADDRESS_1, ADDRESS_2, CITY, STATE,
              ZIP, COUNTRY, PHONE, FAX, CREATED_DATE, ACTIVE
  Types     : ZIP = str ('60601'...), PHONE = str ('312-xxx-xxxx'),
              COUNTRY = str (quasi-uniforme 'United States')

  PFDs documentées dans le cours :
    - ZIP sw '606' → CITY = 'Chicago' (epsilon=0.1, conf=98.3%)
    - PHONE sw '312' → STATE = 'IL' (non testée dans la démo mais mentionnée)
  Note : 37 violations de ZIP→Chicago sont dues à une incohérence de casse
  ('chicago' minuscule vs 'Chicago') — problème de qualité de données
  détecté par la PFD.

  ── data/pfd_validation/t3.csv ─────────────────────────────────────────────

  Source    : Maryland, licences de vente d'alcool.
  Lignes    : 1 077
  Colonnes  : Licensee Name, Street, City, State, Zip, Licensee Number,
              Channel Type, Account Name, Location
  Types     : Zip = float64 (ex : 20852.0), Licensee Number = str

  PFDs documentées dans le cours :
    - Zip → City : 12 violations sur 43 codes postaux (Zip ne détermine pas
      toujours City car un ZIP peut couvrir plusieurs villes)
    - Licensee Number sw 'BBW' → Channel Type = 'On Premise' (conf=95.1%)
  Note : l'algorithme classique généralise 'BBW' en 'B' (conf=94.2%) car
  la lettre initiale suffit à identifier les licences de type "On Premise".

  ── data/pfd_validation/US_Phone_Code.csv ──────────────────────────────────

  Table de correspondance codes téléphoniques → État (USA).
  Peut servir à valider des PFDs de type PHONE_PREFIX → STATE dans t2.csv.

  Résumé     : nombreuses FDs exactes trouvées entre les colonnes structurées

    Department [startswith:'PO'] → Department Name = 'Department of Police'
    (généralisation de 'POL', 'POL1', etc.)

  ── results/discovered_pfds_t2.csv ─────────────────────────────────────────

  Paramètres : epsilon=0.1, min_support=30, k_max=3
  Résumé     : 324 règles, majoritairement liées à COUNTRY='United States'
               (données quasi-uniformes) et à ZIP→CITY/STATE.
  Règle cible du cours (ZIP sw '6'→'United States') → généralisation de
  ZIP sw '606'→'Chicago'.
  Note : la domination de COUNTRY fait remonter des règles triviales en tête.
  Recommandation Tâche 3 : exclure COUNTRY de l'analyse.

  ── results/discovered_pfds_t3.csv ─────────────────────────────────────────

  Paramètres : epsilon=0.1, min_support=20, k_max=4
  Résumé     : 6 règles après généralisation, toutes liées à STATE='MD'
               (Maryland) car toutes les licences sont du Maryland.
  Règle intéressante : Zip sw '2' → State='MD' (tous les ZIP du Maryland
  commencent par 2) — règle géographique réelle.
